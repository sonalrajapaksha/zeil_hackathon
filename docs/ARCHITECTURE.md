# Architecture — Gemini aligned

Next.js App Router + TypeScript + Zod + server-side Gemini API. No authentication, DB, Docker, scraping, or actual ATS submission. Fictional jobs from `src/lib/jobs.ts`. Candidate state local/in memory, consent-based localStorage if added.

- `/api/conversation`: validated candidate turn and recent history to Gemini; returned reply and evidence-bearing suggestions. Optional controlled function-calling uses model-selected `propose_profile_updates` with server validation, pending-only state and tool result sent back. No model authority to confirm facts.
- `/api/application`: confirmed facts + server lookup of fictional job ID → Gemini draft → validated application package. Never fabricate achievements.
- `/api/cv-import`: bounded MIME-checked PDF/image files → Gemini native multimodal understanding → Zod-checked unconfirmed extracted facts. Do not store files persistently.
- `/api/profile-proposals`: bounded completed candidate voice answer → strict, source-checked pending skills/experience/education; no confirmation authority, full history or audio.
- Task 13 optional Gemini Live interview: `/api/live-token` issues a constrained ephemeral credential; `LiveVoice.tsx` manages the native Live WebSocket, microphone PCM through `public/live-pcm-worklet.js`, playback and cleanup. It remains disabled by default through server configuration, requires explicit microphone consent and has a complete text alternative. Async HTTP chat is **not** the Live bonus.

Server secrets only: `GEMINI_API_KEY` (not NEXT_PUBLIC), `GEMINI_MODEL`. Validate output even when schema-constrained; fail gracefully, preserve input, respect timeouts, avoid logging personal data. Protect public judge endpoint with appropriate bounds/rate controls while not requiring judge login. Tool calls dispatch real developer functions; normal button clicks alone aren't Hands.

## Voice-first presentation boundary

The redesign changes page composition, `HeroPreview`, Live presentation and CSS; provider routes, contracts, transport, audio encoding and resource lifecycle stay unchanged. The welcome voice CTA only sets local presentation state and enters the workspace. Opening the consent panel does not request the microphone, an ephemeral token or a text turn. The text CTA uses the existing conversation start handler.

`LiveVoice` derives a visual state from lifecycle, active playback sources, mute, interruption status and errors. CSS drives concentric rings. A presentation-only effect branches the existing microphone source into an unconnected AnalyserNode, samples time-domain data at up to 20Hz and updates only the SVG path. It never connects the analyser to speakers or modifies PCM sending/playback, and disconnects/cancels its frame on mute, stop or unmount. No animation framework or high-frequency React state is used. No silent interval is classified as model thinking or candidate speech. `HeroPreview` is a local, labelled fictional example with CSS animation and pause/replay state, never a provider session.

Live transcripts remain in memory. Completed candidate input transcription automatically enters a bounded queue (12 answers, 4,000 characters each), processed one at a time through `/api/profile-proposals`. Partial input and interviewer output are excluded. Input transcription completion is preferred; uninterrupted turn completion is the fallback. Skip/clarify command turns are suppressed. Shared validation requires exact source evidence, filters sensitive claims and deduplicates suggestions. Shared pending-only merging preserves candidate edits and existing confirmed facts. Extraction failures offer explicit retry independently of microphone health; leaving/resetting cancels pending work. Successful queued raw answers are discarded.

Every suggestion still requires candidate review and approval before application generation or persistence. Only confirmed profile claims and their evidence are retained by existing browser storage. Optional “Review this answer in text” remains available for transcription correction. There is no automatic evidence-to-opportunity mapping. Audio capture, encoding, WebSocket transport, playback and cleanup remain unchanged.

## Unified interview modes

The interview workspace selects Speak or Type through one native radio group. `preferences.interviewMode` is optional in the versioned saved profile: an unset value defaults to Voice, while an explicit choice persists with the candidate's other preferences. Type continues to use `/api/conversation`; Speak continues to use the existing Gemini Live WebSocket and `/api/profile-proposals` pipeline. Both update the same pending-only Career Canvas, but the backends retain separate conversation histories. The interface states that a Live session starts a new conversation and preserves the text history and shared profile rather than implying cross-backend context transfer.

`LiveVoice` remains mounted when Text is selected, but returns no interface. This retains transcript turns and lets an already queued evidence extraction finish. Voice-to-Text selection during an active or connecting session first presents an explicit warning; confirmation makes the existing availability cleanup stop microphone capture, playback, socket and audio resources. Text-to-Voice only displays the ready state: Live access is requested after the separate Start conversation action. Reviewing a voice answer in Text uses the same confirmation before stopping Live, preserving the answer in the editable field and selecting Text. Navigating out of the interview still disposes Live resources and clears the parent session-active flag.

The Live transcript uses an explicit `aria-expanded` button and remains collapsed by default. Transcript entries stay in component memory when hidden; completion state distinguishes partial from finalized provider transcript updates. Streaming updates do not open the disclosure, move focus or create a live region. The Career Canvas uses a native `<details>` disclosure around the existing editor. Its compact summary reads counts and the latest claim from the in-memory candidate profile; new evidence does not expand it. The same summary follows the interview on mobile instead of switching panels, so profile review does not hide or stop a conversation. No provider route, API contract, audio encoding, session handling, evidence validation or downstream workflow changed for this presentation redesign.

## Goal-directed interview controller

`src/lib/interview-controller.ts` is the deterministic progression state machine. Text requests carry its validated state and the current `CandidateProfile`; the server uses globally extracted, evidence-checked suggestions to update the profile before choosing the next section question. Introduction advances to work experience, projects, education, a final review and explicit completion. Candidates can skip a section, decline another entry, or end early. Guided entry counts are capped at two per section; profile extraction is not capped. Corrections get a distinct controller event key, and repeated event IDs are idempotent. Canvas claims retain source message IDs alongside quoted evidence; corrections remove unconfirmed claims tied to the replaced source while confirmed details remain protected.

The browser remains the canonical in-session owner of `CandidateProfile` and controller state. Voice extraction accepts only finalized input turns, passes resulting suggestions into the same profile merge and advances that shared controller. It does not call the text conversation route or treat partial transcript events as evidence. Each new Live session receives the current section goal and a bounded summary of up to six experience, four education and eight skill labels, disclosed next to microphone consent. Live model prompts during an already active socket session remain model-generated and are not synchronously replaced by the controller; after switching modes, the shared controller guides text and any newly started Live session. Controller completion stops an active voice session. Profile `experience` entries currently represent both jobs and projects, distinguished by candidate/model supplied title text; this is a transitional limitation of the existing Canvas contract. Evidence deduplication merges exact same-label entries and preserves candidate-confirmed content. Entry-to-message links and controller progress exist in session memory only; only confirmed profile facts are persisted.
